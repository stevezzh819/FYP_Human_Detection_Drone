# UART Communication Architecture in This Project

UART, short for Universal Asynchronous Receiver-Transmitter, is one of the simplest ways for two digital systems to exchange serial data. In a UART link, the two endpoints agree on electrical levels, baud rate, frame format, and byte timing, but they do not share a clock line. That is the key idea behind the word asynchronous: each side samples the line based on timing agreed in advance rather than on a separate clock signal. Microchip’s UART documentation describes UART as an asynchronous serial communication channel used to communicate with peripheral devices and host systems, typically in a two-wire full-duplex arrangement with a transmit line and a receive line. That description matches the architecture in this repository very closely, because the ESP32-C3 SuperMini and the Crazyflie exchange data over one TX line and one RX line at a fixed configuration of 57600 baud, 8 data bits, no parity, and 1 stop bit. See Microchip’s UART overview here: [Microchip UART overview](https://ww1.microchip.com/downloads/en/DeviceDoc/S17.pdf).

Crazyflie itself is also a reasonable platform for UART-based extensions. Bitcraze’s own UART communication guide for Crazyflie points users to `UART2` on the right expansion connector, specifically `TX2` and `RX2`, as the normal pins for serial experiments. Bitcraze’s expansion-deck documentation also warns that CPX uses `UART2` by default when enabled, which is relevant here because this project implements its own custom bridge on that same UART path instead of adopting CPX. This is a useful official comparison point: Crazyflie already treats `UART2` as an extension interface, and this repository repurposes that same hardware lane for a simpler project-specific protocol. See the Bitcraze references here: [Bitcraze UART communication guide](https://www.bitcraze.io/documentation/repository/crazyflie-lib-python/master/development/uart_communication/) and [Bitcraze expansion deck platform notes](https://www.bitcraze.io/documentation/system/platform/cf2-expansiondecks/). A second hardware reference is the Lighthouse deck datasheet, which explicitly mentions UART and I2C communication on the expansion port: [Bitcraze Lighthouse deck datasheet](https://www.bitcraze.io/documentation/hardware/lighthouse_deck/lighthouse_deck-datasheet.pdf).

In this project, the UART system is built as a deliberately lightweight custom protocol between an external ESP32-C3 SuperMini and the Crazyflie STM32. The repository does not contain a written design memo describing why this exact protocol was chosen, so the design rationale in this paragraph is an engineering inference from the implementation. The protocol appears to have been designed around a very specific need: the ESP32 does not need to stream large arbitrary data structures to the Crazyflie during flight, but it does need to deliver a small number of thermal-inference results reliably and repeatedly. For that reason, the code uses a compact binary frame with two sync bytes, one type byte, one length byte, a bounded payload of up to 64 bytes, and a 16-bit CRC. This is simpler than adopting a larger framework such as CPX, easier to debug on both microcontrollers, small enough to parse byte by byte in a FreeRTOS task, and robust enough to recover from line noise because the parser can resynchronize on the fixed header bytes `0xAA` and `0x55`. In practical terms, the project uses UART as a transport layer for a custom application protocol rather than using UART as a terminal or shell channel.

The data path begins at the thermal sensor, not at the UART port. On the ESP32 side, the AMG8833 thermal array is connected over I2C, not UART. The active driver lives in `espcontrol/crazyflie_esp/main/amg8833.c`. In `amg8833_init()`, the ESP32 configures `I2C_NUM_0` on SDA pin 8 and SCL pin 9 at 400 kHz, probes the default AMG8833 address `0x69`, falls back to `0x68` if needed, and then writes the normal-mode, reset, and frame-rate configuration registers. The actual sensor data flow is then handled by `amg8833_read_pixels()` and `amg8833_read_thermistor()`. `amg8833_read_pixels()` reads 128 raw bytes starting at register `0x80`, which corresponds to 64 pixels times 2 bytes per pixel, and converts each raw sample into Celsius with `amg8833_pixels_raw_to_celsius()`. `amg8833_read_thermistor()` reads the on-chip thermistor registers and converts that raw reading with `amg8833_thermistor_raw_to_celsius()`. In other words, the sensor-to-ESP32 leg is an I2C acquisition stage, and the UART system starts only after the ESP32 has already converted those raw thermal readings into useful temperature values.

Once the ESP32 has a fresh 8x8 temperature frame, the code in `espcontrol/crazyflie_esp/main/crazyflie_esp_main.c` performs the human-detection logic locally. The main loop first captures a background frame, then repeatedly reads the 64-pixel array and thermistor temperature, and passes them into `run_human_inference()`. That function applies a background-comparison strategy and an ambient-relative strategy at the same time. A pixel becomes part of the foreground mask when it is sufficiently hotter than ambient or sufficiently hotter than its stored background value. The code then finds the largest connected blob with `largest_blob_stats()`, computes blob statistics such as size, mean temperature, maximum temperature, and horizontal center position, and finally applies temporal hysteresis so that a detection must remain present for multiple consecutive cycles before it becomes a stable human detection. The result is not a raw thermal frame but a compact inference summary containing a boolean detection flag, a confidence score, a horizontal direction estimate, and two representative temperatures. This choice is central to the protocol design: the live UART link does not carry all 64 pixels to the Crazyflie in the active implementation. It carries a small, already-processed semantic result.

The actual serialization of that result happens in `send_detection_to_crazyflie()` in `crazyflie_esp_main.c`. That function constructs an 11-byte payload. Byte 0 is the human-detected flag. Byte 1 is the confidence value. Byte 2 is the signed direction encoded as an `int8_t`. Bytes 3 and 4 contain `max_temp_x100` in little-endian form, meaning the maximum pixel temperature multiplied by 100 to avoid sending a floating-point value. Bytes 5 and 6 carry the thermistor temperature, also multiplied by 100 and serialized little-endian. Bytes 7 through 10 carry a 32-bit timestamp in milliseconds, again serialized in little-endian order. This payload is then handed to `uart_cf_send_packet()` with type `UART_CF_TYPE_HUMAN_DETECT`. So, in protocol terms, the ESP32 performs the application-layer reduction first and the UART packetization second.

The low-level ESP32 packet builder lives in `espcontrol/crazyflie_esp/main/uart_cf_comm.c`. `uart_cf_init()` configures `UART_NUM_1` with the selected TX and RX pins and enables an ESP-IDF UART driver with RX and TX buffers. `uart_cf_send_packet()` then builds the exact on-wire frame. The frame format is symmetric and simple: header byte 0 `0xAA`, header byte 1 `0x55`, packet type, payload length, payload bytes, CRC low byte, and CRC high byte. The CRC is not computed over the header bytes; it is computed over the type byte, the length byte, and the payload bytes. This is a useful design choice because it makes header scanning independent of CRC verification. The ESP32-side parser is the mirror image of the sender. `uart_cf_receive_packet()` reads bytes from the UART driver one at a time, hands each byte to `uart_cf_consume_byte()`, and returns a complete packet only when the entire frame has been reconstructed and its CRC matches. The parser is implemented as an explicit state machine with states for waiting on each part of the frame, which is the right style for small embedded links because it gives deterministic control over resynchronization and invalid-length handling.

There is also a reverse-direction receiver on the ESP32, but it is narrower than the forward path. In the main loop of `crazyflie_esp_main.c`, the code repeatedly calls `uart_cf_receive_packet()` and `uart_cf_parse_message()`. At present, `uart_cf_parse_message()` only recognizes `UART_CF_TYPE_COMMAND` and only implements one active command: `UART_CF_CMD_SET_THRESHOLD`. The command payload encodes a threshold value as a signed 16-bit integer scaled by ten, which the transport layer stores as `s_detection_threshold_c`. An important project-specific nuance is that this reverse command path is only partially active in the current repository. The active `crazyflie_esp_main.c` does not actually call `uart_cf_get_detection_threshold_c()` when it runs inference, so changing the threshold over UART is supported by the transport code but not consumed by the current active inference function. The legacy file `crazyflie_esp_main_legacy.c` does use that threshold variable, which suggests that threshold control was an earlier design path and the transport support remained in place after the inference model evolved.

On the Crazyflie side, the first stage is not the bridge module but the hardware UART driver in `crazyflie/crazyflie-firmware/src/drivers/src/uart2.c`. `uart2Init()` configures `USART2` for 8N1 operation at the baud rate passed in by the bridge layer. It maps UART2 onto GPIOA pin 2 for TX and GPIOA pin 3 for RX, enables the peripheral clocks, configures the RX not-empty interrupt, and creates a FreeRTOS stream buffer for received bytes. This is an important architectural detail: bytes do not go directly from the hardware interrupt into the parser. Instead, `USART2_IRQHandler()` reads each received byte from the STM32 peripheral and pushes it into `rxStream` with `xStreamBufferSendFromISR()`. That isolates the interrupt handler from the higher-level packet parser and lets the parser live safely in task context. Transmission works similarly in the other direction through interrupt-driven send logic and, when needed, DMA-backed helpers.

The second Crazyflie stage is the application bridge in `crazyflie/crazyflie-firmware/src/modules/src/esp_uart_bridge.c`. `espUartBridgeInit()` initializes `uart2` at 57600 baud, sets up a mutex, and marks the bridge active. `espUartBridgeTask()` then becomes the long-running task-level consumer of incoming bytes. It waits for the firmware system start, reads bytes from `uart2GetCharWithTimeout()`, hands them into `consumeByte()`, and when a frame completes successfully it passes the resulting packet into `handlePacket()`. The parser in `consumeByte()` is deliberately symmetrical with the one on the ESP32. It waits for `0xAA`, then `0x55`, then type, then length, then payload, then the two CRC bytes. It drops invalid lengths greater than 64 bytes, rebuilds the CRC input buffer from type, length, and payload, recomputes the CRC locally, and only then accepts the frame. This symmetry is one of the strengths of the protocol: both sides apply the same framing rules and the same integrity check, so it is easy to reason about failures.

The packet decode logic in `handlePacket()` shows clearly what this protocol is actually used for today. If the packet type is `ESP_UART_TYPE_HUMAN_DETECT`, the Crazyflie interprets the payload as a thermal-perception summary. It decodes the detection flag, confidence, direction, maximum temperature, thermistor temperature, and source timestamp, then stamps the packet with a local Crazyflie receive time in milliseconds. The decoded values are stored in `latestHumanSample`, protected by a mutex, and mirrored into the `espUart` log group for optional telemetry visibility. The parser also contains a compatibility branch for 10-byte payloads, which indicates the project once used an older human packet layout before adding the explicit direction byte. If the packet type is `ESP_UART_TYPE_COMMAND`, the Crazyflie interprets it differently and can issue high-level takeoff or land requests through `crtpCommanderHighLevelTakeoffWithVelocity()` and `crtpCommanderHighLevelLandWithVelocity()`. If the packet type is `ESP_UART_TYPE_TEST_TEXT`, the Crazyflie just records the text. That means the protocol is already designed as a typed link with room for future message families, even though only one telemetry family is heavily used in the current active flow.

Once the human packet has been accepted on the Crazyflie, the data moves into flight logic through a clean accessor rather than by re-reading log variables. In `examples/demos/app_wall_following_demo/src/wall_following.c`, the function `updateHumanPerception()` calls `espUartBridgeGetLatestHumanDetectionSample()`, copies out the latest sample, applies a freshness timeout of 300 ms, and derives the dashboard-facing variables such as `humanDetected`, `humanConfidence`, `humanDir`, `humanPacketFresh`, `humanHoldTimeS`, and `humanStable`. This is an important design improvement compared with treating the UART bridge as a logging subsystem. The mission logic reads from the bridge’s structured state and then separately exposes selected values to the dashboard as `app.*` log variables. In other words, UART carries the ESP32 perception result into the Crazyflie, the bridge turns that byte stream back into typed fields, and the mission layer consumes those typed fields to decide behavior.

The CRC strategy in this project is also worth documenting carefully because it is one of the main reasons the custom protocol is reliable enough for flight use. Both `uart_cf_comm.c` on the ESP32 and `esp_uart_bridge.c` on the Crazyflie implement the same bitwise CRC routine. The code starts with an initial value of `0xFFFF`, XORs each input byte into the upper byte of the CRC state, shifts the register most significant bit first, and applies polynomial `0x1021` whenever the high bit is set. Microchip’s CRC documentation lists the same core parameters for CRC-CCITT in its GET_CRC reference: 16-bit CRC, polynomial `x^16 + x^12 + x^5 + 1`, hexadecimal `0x1021`, seed `0xFFFF`, with the most significant bit shifted first. See Microchip’s CRC reference here: [Microchip CRC-CCITT parameters](https://onlinedocs.microchip.com/oxy/GUID-85C6D874-3EAA-4549-9EBC-46E827CEF407-en-US-1/GUID-03B2EC27-2C66-4F0B-A1F0-9FB1C957E0FA.html). A second useful reference is Microchip TB3128, which also shows the CRC-CCITT polynomial `0x1021` and an initial value of `0xFFFF` in a practical embedded implementation: [Microchip TB3128 CRC note](https://ww1.microchip.com/downloads/aemDocuments/documents/OTH/ApplicationNotes/ApplicationNotes/90003128A.pdf). In this repository, the CRC is appended low byte first and high byte second, and both sides reconstruct it in the same order before comparison.

The most important system-level point is that the active project is not a fully bidirectional perception-fusion loop yet. The forward path is real and active: AMG8833 over I2C into the ESP32, human inference on the ESP32, compact UART packet from the ESP32 to the Crazyflie, structured decode on the Crazyflie, then mission logic and dashboard telemetry. The reverse path exists only in a limited sense. `espUartBridgeSendPacket()` can send packets from Crazyflie to ESP32, and `espUartBridgeTask()` already uses that function to transmit a periodic test string. The ESP32 parser can also accept command packets and update a stored threshold variable. However, after tracing the active code carefully, there is no implemented path that serializes Crazyflie multiranger distance measurements and sends them back to the ESP32 to increase the human-detection confidence. The multiranger data are processed locally on the Crazyflie in `wall_following.c` by reading `range.left`, `range.right`, `range.front`, and `range.back`, and those values are forwarded to the Python dashboard through the normal Crazyradio and CRTP log system in `tools/radio_wall_follow_dashboard.py`. That is a separate telemetry path from the UART bridge. So the correct statement for the current repository is that distance data influence flight logic and dashboard visualization on the Crazyflie side, but they do not currently travel back to the ESP32 as part of the active human-detection loop.

This distinction matters when explaining the protocol logically. The current protocol was built around semantic compression. The ESP32 does the heavy thermal interpretation close to the sensor and sends only what the Crazyflie needs for decision-making. That keeps the UART bandwidth low, keeps the parser simple, and avoids burdening the Crazyflie with thermal image processing. The downside is that the protocol is presently centered on a summary message, not on sensor fusion in both directions. If the next project step is to raise confidence using wall distance or front-range context on the ESP32, then the existing protocol is a good base but it would need one more message type, one more payload definition, and one more parsing branch on the ESP32 side. As the code stands today, the UART layer is already robust and extensible, but the actual application-level use of the reverse direction is still limited.

Taken together, the system is best understood as a layered pipeline. The AMG8833 delivers 8x8 thermal data over I2C to the ESP32. The ESP32 turns that raw data into a human-detection decision with confidence, direction, and temperature metadata. That decision is serialized into a custom UART frame protected by CRC-CCITT and transmitted to the Crazyflie. The Crazyflie receives the byte stream through `USART2`, buffers it safely in FreeRTOS, validates it with the same CRC routine, reconstructs a typed sample, and then exposes that sample to mission logic and telemetry. The dashboard is downstream of the Crazyflie, not downstream of the ESP32, so it sees the mission-state variables and range sensors over CRTP logs rather than over the custom UART link. That is the real protocol architecture implemented in this repository today.
